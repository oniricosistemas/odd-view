# Contributing to odd-view

Thanks for helping improve odd-view. Use the GitHub issue forms when they fit; blank issues remain enabled for reports that do not fit those forms.

## Reporting bugs

Use the **Bug Report** form. Include exact reproduction steps, expected and actual behavior, and the odd-view/runtime version when relevant. Redact secrets and private project data.

## Suggesting features

Use the **Feature Request** form. Describe the user problem, desired outcome, and concrete examples or acceptance criteria. Keep each issue focused on one outcome.

## Maintainer triage and approval

Issues are not approved automatically. A maintainer reviews each report for relevance, evidence, scope, duplicates, and a clear outcome. After that review, the maintainer may manually apply `status/approved` to indicate that the issue is accepted for work. The label does not promise a delivery date or assign the work to a specific contributor. Until a maintainer applies it, an issue is unapproved; labels such as `bug` and `enhancement` describe issue kind only.

Pull requests should reference the issue they address and include a concise summary and the checks that were actually run. Select exactly one `type:*` label and apply the matching label from the repository's label manifest. Maintainers decide when an issue and pull request are ready to merge.

Policy and label definitions are in `.github/labels.yml`; the pull request checklist is in `.github/PULL_REQUEST_TEMPLATE.md`.
